## Bugs to fix first

### O1 — P1: Historical result tables are mistaken for completed, reproducible campaigns

**Location:** [baseline/scheduler.py:100](../../../baseline/scheduler.py#L100), `:118–153`, `:156–166`, `:313–316`.

`fold_done` calls a fold scoreable when `results.csv` and `template.pdb` exist, without checking any design structures. The new clone contains historical CSVs for five folds under the default `baseline/repro`, but no `designs` directories. `repair_merged_folds` copies the current configured template into those directories, after which all five folds are marked complete. This is not just a possible interrupted-run edge case: the default documented scheduler command encounters this state in the clean repository.

**Executed evidence:** The read-only dry-run returned `folds=6 chunks=24 todo=4 (done=20)` and proposed template repair for ankyrin, barrel, iglike, solenoid, and top7. All five lack their referenced design structures. Only four TIM chunks remain queued. In contrast, subsequent `add_rmsd.py:69–72` or `add_ipsae.py:62–66` rejects missing artifacts. The integration notes saying a dry-run planned 24 chunks are true for total planning, but should not be read as all 24 being queued.

**Consequence:** A fresh reproduction can skip almost the entire experiment and retain old numbers as if generated by the requested run. Copying a current template can also mislabel historical outputs when configuration changed.

**Fix:** Separate immutable archived measurements from live run directories. Define a versioned completion manifest containing the run identity, exact expected candidate/trajectory counts, and required artifact checksums. A historical CSV alone must never satisfy completion. Legacy template repair should require verified provenance and existing referenced artifacts, or fail with a migration message.

**Acceptance:** On a clean checkout, the current historical tables must not satisfy a new campaign's completion check. Test CSV-only archives; missing/truncated PDB/pickle; missing template; truly completed legacy runs; and valid manifest-backed completion. A dry-run must report the same decisions without writes.

### O2 — P1: Resume and score caching ignore inputs, settings, and requested counts

**Location:** [baseline/scheduler.py:94](../../../baseline/scheduler.py#L94), `:156–166`; [baseline/score_af2.py:59](../../../baseline/score_af2.py#L59), `:65`; `score_boltz2.py:128`, `score_esmfold.py:105`, `score_openmm.py:148`. Main-driver reuse risk: `FoldCraft.py:102,260–268`, `biopython_utils.py:75–78`.

Completion is keyed only by path/file existence, and scores only by a nonmissing scalar column. Neither checks changed target/template content, hotspots, requested trajectories, chunk size, source/model version, scorer settings, or RNG seed. `FoldCraft.py` also leaves an old final `results.csv` present while replacing artifacts in a reused output directory, so a failed new run can leave a stale completion marker alongside new partial results.

**Executed evidence:** A chunk completed with one trajectory and hotspot `1` is reused when changed to ten trajectories and hotspot `55–60`: the scheduler queues zero chunks. The actual AF2 scorer is invoked first with one target/hotspot, then another; a stub records only the first prediction call because the second request is silently skipped. The same scalar-only cache pattern is source-confirmed in all four scorers.

**Consequence:** Changed experiments can silently inherit old measurements. Baseline-versus-improvement comparisons are not reliable unless users manually enforce unique directories and remove stale scoring columns.

**Fix:** Hash resolved config, inputs, code/dependency/weight versions, relevant seeds, and scorer version into run/score identities. Refuse mismatched reuse by default, or create a new run. Distinguish resume from overwrite explicitly. Store per-scorer results separately with their identity; include all required metric fields/status before treating a row as complete. Record original chunk index and explicit trajectory IDs so repartitioning cannot relabel work.

**Acceptance:** Changed target bytes at the same filename, sequence, hotspot, count, chunk size, scorer parameters, or model version must cause a clear mismatch or recomputation; an unchanged restart must reuse the exact completed work. Starting a new run in a completed directory must not leave a valid old completion marker for the new run.

### O3 — P1: Interrupted merge can become permanently marked complete; partial checkpoints are not atomic

**Location:** [baseline/scheduler.py:212](../../../baseline/scheduler.py#L212), `:231–232`; [biopython_utils.py:75](../../../biopython_utils.py#L75). Scorer rewrites: `score_af2.py:80,83`, `score_boltz2.py:154,156`, `score_esmfold.py:124,126`, `score_openmm.py:169,171`, `add_rmsd.py:75`, `add_ipsae.py:75`.

`merge_chunks` copies `template.pdb` before writing `results.csv` directly. A disk error/interruption during that write leaves both files present, which `fold_done` accepts on the next attempt. The main driver's final `os.replace` is atomic, but each update overwrites the same `.partial` file directly, destroying the previous recoverable checkpoint if interrupted. Scorers overwrite the source CSV directly, potentially losing both design data and previously acquired expensive scores.

**Executed evidence:** Fault-injecting an interrupted `DataFrame.to_csv` that writes only a header then raises leaves a zero-row merged CSV. `fold_done` returns true and `filter_todo` schedules no recovery.

**Fix:** Write every checkpoint/table to a unique temporary file in the same filesystem, validate it, flush as appropriate, and atomically replace the prior checkpoint. Publish completion only after every required artifact and row count is validated. Keep the previous good checkpoint until the new one is durable; publish merged outputs as a transaction/staged run directory. Atomic replacement alone does not solve concurrent updates (O4).

**Acceptance:** Inject failures before, during, and after checkpoint/merge writes, including disk-full and process termination. Restart must recover either the previous complete version or unfinished work, never accept a partial table as completion. Readers must never observe truncated CSVs.

### O4 — P1 when scorers run concurrently: Successful scoring jobs overwrite each other's results

**Location:** [baseline/score_af2.py:59](../../../baseline/score_af2.py#L59), `:78–83`; [baseline/score_esmfold.py:99](../../../baseline/score_esmfold.py#L99), `:122–126`; identical whole-table snapshot/write pattern in Boltz-2, OpenMM, RMSD, and ipSAE tools.

Each scorer loads the whole CSV once, adds its own columns, and rewrites its in-memory snapshot. Two independent scorers naturally run concurrently on different hardware (e.g. GPU AF2 and CPU OpenMM), but whichever writes last removes the other process's additions. Atomic file replacement by itself preserves the lost-update bug.

**Executed evidence:** Interleaved the actual AF2 and ESMFold `main()` functions with deterministic stub predictions. ESMFold successfully writes its metrics after AF2 reads the original table; AF2 then successfully writes its older snapshot. Final columns contain AF2 metrics and no ESMFold metrics.

**Fix:** Prefer immutable design manifests plus separate versioned result tables per scorer/run, joined by validated candidate ID. Alternatively serialize writes under a lock and reread/merge by candidate identity before committing; also address same-scorer duplicate work. Retain explicit pending/success/error states and reasons rather than overloading missing numeric cells.

**Acceptance:** Run two scorers with barriers forcing both to read before either writes; all metrics and immutable candidate data must survive. Also verify crash recovery and two instances of the same scorer. Repeat O3 failure injection for the chosen persistence backend.

### O5 — P2: A retry marked “solo” does not reserve the GPU against new neighbors

**Location:** [baseline/scheduler.py:184](../../../baseline/scheduler.py#L184), `:343–348`, `:378–380`.

`can_launch` checks whether the *incoming* chunk is solo and the GPU already has committed memory. It never checks whether an existing job is solo. If external GPU memory is freed after the retry starts, an ordinary queued chunk can be launched onto the same GPU, recreating the pressure that the solo retry was meant to remove.

**Executed evidence:** A realistic mocked full `run()` starts a 6 GB job while an external tenant leaves only 10 GB free. The job fails, is queued normally by the real retry logic, and restarts solo. External memory then becomes free; the scheduler immediately launches a 14 GB ordinary job alongside it on the same 24 GB GPU. No synthetic queue reordering was used.

**Fix:** Track GPU exclusivity separately from committed memory; while a solo job is running, block every other launch on that GPU. Release the reservation when reaped. Preserve per-attempt logs rather than overwriting `chunk.log` when retrying.

**Acceptance:** Test the orchestration loop with varying GPU free-memory readings, a failed packed job, its solo retry, and a waiting ordinary job. Assert zero overlapping jobs during the retry. Existing `can_launch` unit tests check only the incoming job and miss this lifecycle case.

### O6 — P2: Campaign shell runner reports process success after every design job fails

**Location:** [baseline/run_campaign.sh:13](../../../baseline/run_campaign.sh#L13), `:16–24`.

The runner catches a failed Python invocation with a successful `echo FOLD_FAIL`, then prints `CAMPAIGN_DONE` and exits zero. The piped `while` loop also makes a naive parent-shell failure counter ineffective.

**Executed evidence:** Put a fake `python` executable returning exit code 23 ahead of PATH, then ran the unchanged shell script. It printed six `FOLD_FAIL` lines, `CAMPAIGN_DONE`, and returned zero. No output artifacts or inference were created.

**Fix:** Either fail fast using an appropriate strict-shell pattern or collect errors in the parent shell (e.g. redirected/process-substitution input instead of a pipeline), emit an explicit incomplete summary, and return nonzero if any fold fails. Quote the `wc` redirection path as well. `run_repro.sh` already uses strict mode, so share one campaign entry point instead of maintaining divergent policies.

**Acceptance:** All success returns zero; one or all failures return nonzero with failed fold IDs; malformed config and missing inputs fail clearly. Include output paths with spaces.

### O7 — P1/P2: Bound generation and clean up children on scheduler failure

**Location:** [FoldCraft.py:386](../../../FoldCraft.py#L386), `:414,454,464`; [baseline/scheduler.py:333](../../../baseline/scheduler.py#L333), `:343,346,366–372`.

**Source-verified, carried forward:** `--sample` still has no maximum trajectory count or time budget. An always-rejecting model never reaches the requested successes (P1 uncontrolled compute). The finite scheduler mode does not fix the direct sampling mode.

**Source-verified new orchestration issue:** `run()` has no `try/finally` around spawned children and no termination/reaping handler. If a GPU telemetry call, subsequent launch, polling, or parent process raises while children are live, those children and open logs are not deliberately cleaned up by the scheduler (P2). Re-running can launch duplicate workers into the same chunk output directory while earlier children continue. This risk is source-verified; no real orphan GPU process was created.

**Fix:** Explicit attempt/time budgets and terminal incomplete status, plus per-attempt audit rows including rejection reasons. Add scheduler-managed process groups, graceful cancellation, bounded termination/escalation/reaping, worker ownership records, and an exclusive campaign/chunk lock. Handle telemetry failures explicitly with bounded retries or cleanup.

**Acceptance:** Always-rejecting model terminates within the configured budget; accepted counts remain exact; interrupt/fail telemetry while a fake child is live and assert it is reaped or deliberately detached with recoverable ownership. A second scheduler must not execute a chunk already owned by a live worker.

## Performance improvements after correctness and reproducibility

These are opportunities, not new measured speedups. The existing MPNN reuse, per-trajectory AF prediction reuse, map caching, and prior reported ~24% improvement are already in this baseline and must not be counted again as proposed fixes.

### OP1 — High-value opportunity: Compact artifacts and optional trajectory history

**Location:** `FoldCraft.py:322–323,366–367,412–413,456–457`; reviewed dependency `colabdesign/af/model.py:39`, `af/design.py:251–260`, `af/alphafold/model/modules.py:157`.

Every candidate/trajectory pickles `aux['all']`, including quadratic 128-channel recycling state (`prev_pair`) not used by current ranking/scoring. A float32 `[239,239,128]` pair representation is 27.89 MiB per model. With the current two final design models and one validation model, 40 trajectories × (2 + 5) models implies approximately 7.63 GiB in that array alone; this is a source-derived size calculation, not a measured disk footprint. Correcting the validation model count can increase it further. The default 220-step PAE history alone is 47.94 MiB at L=239 and 839.23 MiB at L=1000, excluding other arrays. Main CLI does not consume animations/history.

**Change:** Versioned compact result schema containing needed confidence, PAE, coordinates, sequence, provenance, and per-model identity; optional debug checkpoints separate from results. Disable/downsample unused trajectory history. Release setup-only objects after copying required host arrays. Design the schema alongside O2–O4 so science-data retention is explicit.

**Benchmark:** Fixed candidate set; measure bytes/candidate, serialization time, peak host/GPU memory, and output read time. All downstream RMSD/ipSAE/scoring must reproduce retained values exactly or within declared serialization tolerance. Test both one-model historical and corrected multi-model outputs.

### OP2 — High-value opportunity: Reuse AF models/features across trajectories and cache compilation

**Location:** `FoldCraft.py:301,352,394,438`; `baseline/score_af2.py:33–40`; `baseline/bench_jax_cache.py:18–49`.

Main design/validation models are rebuilt each trajectory, and the separate AF2 scorer rebuilds every sequence. Constructors reload parameters and rebuild JIT functions. For a 40-trajectory VHH run, source control flow constructs 81 AF objects (one setup plus two per trajectory). Non-VHH adds another setup model. The existing compilation-cache script provides a starting harness but does not prove a speedup or model-state parity on this branch.

**Change:** Persist separate design/validation models per compatible shape/settings; cache processed target features and host parameters. Explicitly reset sequence/optimizer/RNG/history; avoid blanket `clear_mem` that invalidates retained device buffers. Use bounded caches/length buckets for variable lengths with correct padding masks. Enable persistent compilation cache only after version/hardware boundaries and measurements are defined.

**Benchmark:** Cold start plus at least ten warm trajectories at several complex lengths, synchronized GPU timings, compile logs, parameter-load time, total time, peak memory, and unique candidates/GPU-hour. Compare to the corrected baseline under identical seeds and assert sequence/metric/acceptance parity. Model-count corrections are behavioral changes and should not be conflated with a performance experiment.

### OP3 — Measure before implementing: Avoid duplicate validation, tune packing empirically

**Location:** `FoldCraft.py:339,361–374,450–465`; `baseline/scheduler.py:169–190,343–348`.

Low-temperature MPNN may repeat exact sequences, yet every sample is validated and can count toward success. Frequency has not been measured. Scheduler memory values are static estimates; packing can improve throughput but could reduce it through memory pressure/recompilation/I/O, so concurrency is not inherently faster.

**Change/benchmark:** First report exact duplicates and sequence/interface-cluster diversity per target/trajectory. Cache deterministic validation by full candidate/model/input/settings/seed identity without collapsing deliberate ensemble-seed replicates. Compare solo versus packed campaigns at matched budgets; measure completed unique candidates/GPU-hour, aggregate wall time, memory high-water marks, retries/failures, and cache-hit rate. Adopt only statistically supported throughput gains with unchanged outputs and no data loss.
